## C7 事故：新文件的行尾「双重假绿」（收口后才发现）

**现象**：F-9 提交后打新 bundle，`_d6_bundle_verify` 的 **C7 红**：
`i/lf w/crlf`（源库）vs `i/lf w/lf`（clone）—— 同一个 `_f9_artifact_freshness.py`，两个工作区不一致。

**根因**：`_d3_normalize_eol.py` 只扫**已追踪**文件（`git ls-files`）。我这次是
「Write 新文件（LF）→ git add → 提交 → 跑 --apply」，而 --apply 当时报「待处理 4 个」
处理的是 4 个被 Edit 重写过的 md，**新 .py 因为还没 add，根本不在扫描范围内**。

**为什么这是「双重假绿」**（比普通漏检更危险）：
1. `_d3_normalize_eol.py` 复验报「待处理 **0** 个」—— 它看不到那个文件，所以它认为自己全对了；
2. `git status` 也是干净的 —— 索引 `i/lf`、工作区 `w/lf`、属性要求 `eol=crlf`，
   git 按 `text=auto` 归一后认为「无改动」。
**两个检查都说没事，只有跨仓库 clone 一次（C7）才看得见。**

**修**：新文件已入库后补跑 `_d3 --apply`（处理 1 个）→ `w/crlf`；`git add` 一次让 stat 缓存同步
（`git diff` 为空但 `git status` 报 M，是 mtime 缓存，不是内容）；重跑 d6 ⇒ **C1–C9 全过**。

**教训（要写进规矩，不是记在脑子里）**：**新文件的正确顺序是 `git add` → `_d3 --apply` → `check_commit`
→ 提交**；或者把 `_d3` 的扫描源改成 `git ls-files --cached --others --exclude-standard`
（含未追踪）。后者是工具级修法，牵动 D3 契约，登记为 **F-12**（不改判据，只扩扫描源 + 一条自检）。

**顺带一个观察**：C7 的 `diff = set(e_src) ^ set(e_cl)` 用集合对称差，输出顺序不定 ⇒
两行里哪行是源库、哪行是 clone **看不出来**，第一次读差点判反方向（以为源库对、clone 错）。
改成带前缀（`src:` / `clone:`）更容易读 —— 但这属于「红的可读性」，不是判据错，本轮没改。
