一、本次做了什么

四件事，按依赖顺序：

  1. 给 deck 生成器加 Abaqus 方言分支。两个求解器的关键字语言大部分相同，所以是一个 builder + 方言开关，而不是两份会各自漂移的代码。开关只落在三处：输出请求块、少数单字段数据行的尾逗号、*HEADING 出处行。
  2. 写 ODB 结果提取器（abaqus_odb.py，由 abaqus python 执行——odbAccess 只存在于 Abaqus 自己的解释器里）。它把 ODB 转成与 FRD 解析器完全同构的中间 JSON，于是结果归纳那段代码一行都不分支。
  3. 求解器适配层接入 Abaqus：job=/interactive/cpus=1/ask_delete=OFF，求解完成后自动调用提取器。
  4. 双求解器交叉验证（verify_solvers.py）：同一模型两个互相独立的代码各算一遍，比物理结果。这是对适配层最硬的检查。
  5. 给几何加长桁（本轮追加）：上下蒙皮各加 N 条竖式长桁，顶边与蒙皮共节点。顺带修掉窄条网格的退化，并做了「有/无长桁」的对照实验。见第七节。

峰值不作判据。ccx 10.28 MPa vs abaqus 膜 8.45 MPa 差 17.8 %，但这不是可用的比对判据——von Mises 峰值出现在梁肋交汇的几何奇异点，只由各家的平滑/外插选择主导，本身随网格变化。所以本工程把逐节点中位差作为应力判据（0.31 %），峰值只作报告。abaqus 侧同时输出"外表面逐单元峰值"11.78 MPa，那是定尺寸用的数，与 CalculiX 的 2D 口径不可比。

五、两个真 bug（本轮发现，修复后所有数据已重跑）

Bug 1 — 载荷被静默稀释（最阴的一个）

gmsh 会为曲面之外的曲线和点也生成节点，诊断时（几何修复前）本算例有 396 个节点不连接任何单元。载荷按"翼尖所有节点（190 个）"平摊，但其中只有 124 个真正在模型里：

实际施加 = 500 / 190 × 124 = 326.32 N
根部反力之和 = −326.31589 N   ← 精确吻合

结果是之前所有翼盒数字（1.5854 mm / 6.86 MPa）对应的都是 326 N，不是 500 N。 只有静力平衡检查能发现它——位移、应力、雅可比全都"看着合理"。

Abaqus 更不容忍：它删掉这 396 个节点后，直接报 67 个致命错误（"集中力施加在未激活节点上"）并中止。这也是 Abaqus 分支第一次跑失败的真实原因。

修法：meshing.referenced_nodes() 只保留被单元引用的节点。未被引用的节点不参与刚度矩阵，删除是物理等价的，同时让 deck 对两个求解器都自洽。修复后孤儿节点 0，平衡残差 0.000034 %。

注：上面 396 / 190 / 124 是几何修复前的诊断读数。Bug 2 改了梁腹板位置后几何随之变化，当前复跑读数为孤儿节点 408 个、翼尖载荷节点 142 个，*CLOAD 合计 500 N（不再稀释）。

Bug 2 — 梁腹板是斜的，前后梁整个丢失

_points_on_section() 从余弦采样的网格里"挑" x ∈ [0.25c, 0.70c]，但余弦网格上根本没有 0.25/0.70 这两个点：

上表面最近点 x = 261.38   ↓  连起来的前梁斜了 3.225 mm
下表面最近点 x = 258.16   ↑  后梁斜了 7.369 mm

腹板一旦带上弦向跨度，dx ≤ tol 的归类条件就判不出来，8 块腹板全被塞进"上蒙皮"组。后果是 deck 里完全没有 E_FRONT_SPAR / E_REAR_SPAR，而且上下蒙皮单元数严重不对称（2471 vs 1694）。

七、加长桁：竖式长桁（本轮新增）

把 n_stringers_per_skin 从占位的 3 变成真正建出来的几何，默认值改为 0（不加强）——这样既有基线一个数都不用动，长桁按需开启（--stringers N）。

建的是什么

每侧蒙皮 N 条竖式长桁（blade stringer）：位于 x = const 平面、沿展向通长、顶边与蒙皮贴合、底边自由的一片竖板——薄壁盒段里长桁的常规理想化。站位在前后梁之间等分。

三个不明显的地方

  1. 长桁站位必须是蒙皮样条的控制点。板顶边与蒙皮若只是"贴得很近"而非共享边，布尔运算会吐碎片、甚至干脆不连。所以站位被显式插进截面点列（_points_on_section(extra=…)），让样条按构造穿过它。
  2. 长桁也是 dx ≈ 0 的平面，与翼梁判据撞车。原分类器"dx ≈ 0 就是梁"会把每条长桁都当成梁。改为按弦向站位区分——站位严格取在梁之间，两个集合不相交。
  3. 上下不能用 y > 0 判。NACA4412 有弯度：下蒙皮在 0.59c 处 y = −10.3 mm，20 mm 的长桁会伸到 y = +9.7 mm，中心落在 y=0 之上却明明属于下蒙皮。改成与局部盒段中高线比较。

对照组 vs 基线只差 0.02 %（2.3649 vs 2.3654 mm）——说明重组算法对响应几乎中性，所以第三行的差异可以干净地归因给长桁本身：挠度 −6.15 %、峰值 vM −4.7 %。方向合理——长桁贴蒙皮承担轴向载荷，增大弯曲刚度与承力面积。对照 §三 的扫描：翼肋几乎不影响整体弯曲，长桁则直接影响。

交叉验证（verify_solvers.py --case naca4412_wingbox_str3）：PASS · 7 项 —— 节点 7387 完全一致、坐标 float32 一致、max|u| 差 0.277 %、平衡残差 0.000364 % / 0.000281 %、逐节点应力中位差 0.48 %。

长桁是 20 × 500 mm 的窄条，gmsh 默认的 blossom 重组算法在这种长宽比上很差。用 diagnostics/stringer_quality.py 逐组统计后确认：坏单元几乎全在长桁上（444 个三角里的 432 个），蒙皮只是轻微下降（0.52–0.56）。

Abaqus deck / ODB

#坑表现 / 修法
5OUTPUT=2D 是 CalculiX 专有写进 Abaqus deck 直接中止。Abaqus 用 *OUTPUT, FIELD + *NODE OUTPUT / *ELEMENT OUTPUT。
6没加 ask_delete=OFF只要上次留了作业文件，Abaqus 就停在交互式"是否覆盖？"提示上，直到超时。不是可选项。
6b残留 .lck 让作业中止，但 Abaqus 返回 0原因写在 <job>.msg（不是 stdout，也不是 .dat）："Detected lock file … before removing the lock file and resubmitting"。批量跑时会表现为"每个受影响算例都成功-然后-空结果"。适配层启动前清掉自己输出目录里的锁（该时刻它必然是陈旧的）并记日志；同时不再只信退出码——要求有可用 ODB，并回读 .msg/.dat 报出真实原因。
6cAbaqus 在被沙箱隔离的 shell 里会"静默失败"pre.exe 要往 %TEMP%\22207_<job>_<pid> 写 scratch 目录——在工作区之外。写入被拦时它不报权限错，而是表现为：固定 ~19 s 延迟 + Analysis Input File Processor exited with an error + .dat 里一条错误都没有 + ODB 只有骨架没有帧。定位：先用 1 个单元的最小卡片复现（证明与模型无关）→ 再逐一 A/B 掉 ask_delete、路径空格、输出块、并行模式（全不是）→ 最后比对"隔离 / 不隔离"两次调用才锁定。结论：本机跑 Abaqus 必须在不被隔离的 shell 里。
7odbAccess 是"像 dict"而不是 dict三种错法各不相同：frame.fieldOutputs 是 Repository（有 []、keys()，没有 .get()）；instance.elements 是 OdbMeshElementArray（可迭代，没有 keys()）；getSubset(position=) 要符号常量，传字符串报 position; found string…。
8壳应力是 4 分量不是 6 分量实测类型 TENSOR_3D_PLANAR，分量为 (S11,S22,S33,S12)（壳理论平面应力，S33≡0）。而 FRD 是 (SXX,SYY,SZZ,SXY,SYZ,SZX)——两个剪切分量顺序相反。必须按分量标签映射；按下标映射会在分量数变化时静默出错。
9ELEMENT_NODAL 只暴露最外侧两个截面点默认 5 点截面下只给 1 和 5。取 sorted(sp)[len//2] 拿到的是顶面不是中面——典型的"安静地给错答案"。正确做法是壳理论的膜应力 (σ下+σ上)/2。
