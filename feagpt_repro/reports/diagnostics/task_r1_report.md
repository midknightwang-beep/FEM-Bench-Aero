## 6. 已知问题 / 未验证项

1. **§1 的权重是判断，不是测量。** 25/30/35/10 的依据是「该段占 180 天总工作量的比例」，没有客观来源。换一套权重，数会变（按条目数不加权为 43%）。**这是本文最脆弱的一处**，已在 §0 读法② 和 §1 两处声明；若对外引用，必须先说「这是我的估算」。
2. **A3「对外材料单一数字源」未核。** 两份 pptx 的正文数字是否已到当前口径，本轮没有逐页核对（不在 allowlist，且属独立任务）。故 A 段标 ⚠️ 而非 ✅。
3. **D3 行尾的「两端各有锚点」是 T-B1 的实测结论**，本文只转述结论、未复测。若要立项，须先复现「默认 clone 与 `autocrlf=false` 各自哪些锚点绿/红」。
   **本轮新增现场证据（顺手撞到的）**：本轮新建/覆盖的三个文件由编辑器写成 **LF**，`git add` 时 git 报 `LF will be replaced by CRLF the next time Git touches it`。而工作区既有的 `tasks.jsonl` 实测是 **CRLF**（192 行全 CRLF）、git 库里存 LF。⇒ **同一个工作区里，新旧文件的行尾本来就不同源**；这三个文件不是 sha 锚点对象所以本轮无影响，但任何人将来对它们重算 sha，就会撞上 D3 描述的同一堵墙。这条印证了 D3 不是「配置没调对」，而是**工作区状态本身不一致**。
4. **§8 KPI 表里 4 项 ❌ 的判定依据是「没有 artifact」**，不是「跑过但不好」。B1 补算可能发现这些指标本来就好看 —— 届时是「补出一份成绩」，不是「修复一个缺陷」，须走新版号 + 留档（R-A2）。
5. **本文没有任何闸守它。** ROADMAP 不在 S-56 的检查范围（S-56 只查 AGENTS/CLAUDE/CLAIMS 标题），也不在 R-A3 列举的四份文件内。也就是说：**这份文档的正确性完全依赖人工**，下次它漂了不会被闸抓到。这是结构性缺陷，建议后续给「ROADMAP 的状态标记必须指向 C-0xx 或文件路径」建一条静态判据。
