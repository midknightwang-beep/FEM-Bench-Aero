## 1. 立项时的判断是错的（本轮最重要的发现）

F-2 一直记作「`package-lock.json` 被 `.gitignore` 忽略 ⇒ **进不了新库**」。实测发现更准确的说法是：

| 事实 | 值 |
|---|---|
| 主仓是否已追踪 | **是**（blob `2cc9a35c`，与磁盘逐字节一致） |
| `.gitignore` 第 58 行是否仍写着忽略它 | **是**（来自 `98acf48` W4b-2） |
| 公开快照里磁盘有没有 | **有**（2958 B） |
| 公开快照做成库时进不进得去 | **进不去**（`ls-files` 0 条） |

⇒ 它不是「文件没入库」，是**规则与事实自相矛盾**：主仓靠「先被追踪、后加忽略规则」这个历史顺序
侥幸留着（git 对已追踪文件不生效 `.gitignore`），但只要有人做一次常规清理
（`git rm --cached` + 按规则重加），或按快照重建仓库，它就**静默消失**，且**没有任何闸会报**
（R58 的又一形态：无工具读的 = 无闸）。

这也解释了为什么之前几轮反复「发现」它却一直没修：**症状（少一个文件）出现的地方，
和病根（一条陈旧规则）不在同一处**。

## 4. 新发现 F-7（已登记，本轮不修）

做 V2 时顺手量到：**`.gitattributes` 不在公开集里**。

```
classify('.gitattributes') -> (False, '根目录内部材料')
classify('.gitignore')     -> (True,  'KEEP:根目录必需')
```

两者并列在仓库根、作用相同（一个管行尾、一个管忽略），但白名单只收了 `.gitignore`。
后果：第三方 clone 公开库后**拿不到行尾规则**，行尾由客户端 `core.autocrlf` 决定
（Windows 默认 CRLF、Linux 默认 LF）⇒ **T-D3 花一整轮解决的「换机不一致」在公开库侧原样复活**。

这不是「顺手就能改」：它要动 `classify()` 的白名单，属于 D4 判据面，与 F-2 不是同一条变量
（R-A1 单变量）。已写进 ROADMAP §13 第 1 位。

## 5. 自纠：本轮同一个错误犯了三次

在核对「快照 vs 主仓」差集时，三次用 `git ls-files`（默认 `core.quotepath=true`，把中文名转义成
`\346\265\201...`）去和 `find`（输出真实 UTF-8）做 `comm`：

1. 第一次：结论「快照里有个残留文件 `FeaGPT流程复现报告.html`」—— **假的**，该文件在索引里。
2. 第二次：结论「正确路径下 dest 独有 = 0」—— 这次是对的，但只是因为我碰巧加了 `-c core.quotepath=false`。
3. 第三次：结论「旧规则缺 2 个文件（lock + html）」—— **假的**，缺的只有 lock。

**三次都是同一个机理**：两侧编码口径不一致时，`comm` 会把同一文件同时算进「只有左边」和
「只有右边」，**看起来像新发现，其实是量具坏了**。真值只有用同一口径才拿得到
（`git -c core.quotepath=false ls-files` vs `find`）。

⇒ 教训：**比对之前先问「两侧的字是不是同一套字符集」**。这与 D3 的「口径参数漏传 ⇒ 假 FAIL」
（`--spec` 漏传印出 `residual 99.99%`）是同一族 —— 先怀疑量具，再怀疑被测对象。
