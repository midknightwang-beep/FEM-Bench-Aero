## 1. 一句话

方案 B 的三处改动**把目标错误从 21 条清到 0**，但**首轮通过率仍然 0/4（与基线相同）⇒ 一分钱也没省**；
把修复轮早就给出的「允许键清单」前置到首轮（记为 B+）之后，**首轮通过 3/4** —— 「省一轮」的收益属于 B+，不属于 B。

## 2. 为什么先做影子批，而不是直接改 `SYS`

`check_claims.py:2394-2406` 的 **S-39** 要求 C-032/C-033 成绩单的 `provenance.prompt_sha256` == 生成器当前 `SYS` 的 sha256。
**一旦改 `SYS` 常量，四份 prompt-v2 代成绩单立刻与源码不等、S-39 必红**，此时不重跑就提交不上；要重跑就得全量重生成 64 条 × 2 模型 + 重打分（含求解）。

所以分两阶段（契约 §4）：

- **阶段 1（本轮）**：给生成器加 `--sys-file`，`SYS` **常量一个字节不动**（sha 实测仍是 `ce225186…`），跑影子批量化收益；
- **阶段 2（待拍板）**：正式改 `SYS` + 全量重跑 + 更新成绩单。

`--sys-file` 的三条自保（均已实测）：
1. 不传参时行为与旧版逐字节一致 —— `--print-prompt-sha` 仍输出 `ce225186cafa5d55…`（前值）；
2. 不能用于 L2 —— 会把 L2 追加段丢掉，实测 `RC=2` 且在调用模型前退出；
3. 影子 prompt 的 sha 单独记进候选的 `prompt_sha256`，事后可分辨哪批是影子。

## 3. 影子 prompt 怎么产生（确定性，不手抄）

`_psa_build_prompt.py` 从 `gen_candidates_v2.js` **逐字节提取** `SYS`，再施加定点替换：

| 变体 | 改动 | 影子 SYS sha256 |
|---|---|---|
| `b` | C1 顶层 7 块 required 显式化 + C2 `material` 五键 + C3 网格键去 `size` | `73e779808d67cdad…` |
| `bplus` | `b` + C4（各块允许键白名单前置） | `d9c0b02d04119089…` |

三条防呆（任一不满足就退出、不产出 prompt）：
- 提取出的 `SYS` 的 sha256 必须 == 契约 §0.1 前值（防定位错位后拿半截 prompt 去跑）；
- 每处替换**必须恰好命中 1 次**（0 次 = prompt 已变、脚本过期；>1 次 = 会改坏别处）；
- 文本层判据 P1/P2 必须过（`material` 五键名、7 个块名、且含「全部必填」）。

| 类 | 含义 | 基线 v7 | **B** | **B+** |

| Z | `mesh` required（`size_chord/size_span`）缺失 | 6 | **0** | **0** |
| S | `size` 被当自创键拒 | 3 | **0** | **0** |
| O | 其他自创键（`analysis.type` / `bc.edge_support` / `airfoil.n_stringers_per_skin`…） | 10 | 4 | 1 |
| **合计首轮错误** | | **31** | **4** | **1** |
| **首轮通过的题数** | | **0/4** | **0/4** | **3/4** |
| 轮数分布 | | 2,2,2,2 | 2,2,2,2 | **1,1,1,2** |

**判据状态**：P1 ✓、P2 ✓、P4 ✓（M=0）、P5 ✓（S=0）、P6 ✓（`analysis.type` 仍有 3 条 ⇒ 证明只治了 ①②，没顺带治 ③）、P7 ✓（`schema_task.json` / `tasks.jsonl` 的 sha == 前值）。
**P3 ✗**（要求首轮通过率 > 0，B 实测 0/4）。

## 6. 报告 §11 的假设被推翻：「省一轮」不属于方案 B

`task_b1kpi_report.md` §11 写「收益是可量化的省一轮」。实测：**B 清零了 21 条目标错误，但没有一条题因此首轮通过**——因为每道题**同时**还夹着 1–3 个自创键（`analysis.type` 最常见）。

⇒ 只要还有任何一个自创键，闸就不放行，轮数不变。**「省一轮」是一个「全有或全无」的效应，不是「修一部分省一部分」。**

B+ 之所以有效，是因为它把 `gen_candidates_v2.js:220-227` 里**早就存在的 `ALLOWED_HINT`**（原本只在修复轮把错误推回时才给模型）前置到了首轮。

> **机制一句话**：模型首轮写自创键 → 闸拒 → 修复轮里收到「允许键: …」→ 改对。
> 于是 **L1 修复成功率 100% 的本质 = 这份清单在第二轮才出现**。把它挪到第一轮，那 100% 就变成「本来就不需要修复」。

这也给 T-B1KPI 的「L1=100% 是闸严格度的影子」补了机制层的解释。

## 7. 另一个发现：wingbox 那条的两难（新单子候选，未处置）

B+ 里唯一没过的 `L3_naca4412_wingbox_n_ribs3_chord1000` 首轮错在：

```
/airfoil must have required property 'n_stringers_per_skin'
```

而 prompt 的数量铁律写着：**题面提到长桁却没给根数 ⇒ 必须澄清，不得假设、不得填 0**。
`schema_task.json` 的 wingbox 分支又把 `airfoil.n_stringers_per_skin` 列为 **required**。

⇒ 模型只有两条路：**澄清**（但题面其余参数齐全，模型选择了直接产出 spec）或**填一个编造值过闸**。
该条第 2 轮"修好了"，最可能是后者 —— **这会被 R20「静默编造」判据当成合格**。

这条与 N-29 同类（schema 的 required 与语义铁律冲突），但**本轮不动**，只登记。
