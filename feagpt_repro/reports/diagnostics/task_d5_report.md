## 6. 已知问题 / 未验证项（边界）

1. **★ hook 不入库。** `.git/` 不被 Git 追踪 ⇒ **新 clone / 换机后这道闸等于不存在**，必须手动跑一次 `--install-hook`。已写进 `AGENTS.md` §0 的 ⚠ 块和 `CLAUDE.md`，但**没有任何闸检查「hook 是否已安装」** —— 这是本闸最大的缺口，等同 R58「无工具读的 = 无闸」。
2. **本闸不进 `negative_controls.py` 的 69 条计数。** 理由：负控套件每条都绑定判分 artifact，加 NC-68 会牵动 69→70 → CLAIMS C-019 计数链 → INDEX 累计数 → S-44/NC-49 的循环依赖（这条坑 10-30 已踩过两次）。本闸的自我验证改用 `--self-test` 9 向 + 隔离仓库端到端实测，比负控更接近真实故障形态。
   **★ 但这是有代价的**：只跑负控的人看不到这条闸的验证结果。若后续要把流程闸纳入统一套件，须先解决计数链的循环依赖。
3. **`--no-verify` 可绕过。** 这是 git 的设计，闸本身拦不住。已在文档写明「绕过 = 主动放弃这条闸，须在报告里写明原因」。
4. **白名单当前只有 1 条**（第十四轮复评 md）。D4 仓库卫生立项时会重新审视它是否该入库。
5. **未验证**：多个 worktree / 子模块场景未测（本仓库不用）。

## 7. 本轮自己踩的两个坑（都是判据类，值得记）

1. **★ 闸把自己绊倒了**：自检第一版 **9 向里 7 向误报红** —— 原因是白名单文件 `commit_allowlist.json` 自己在工作区是**未追踪**的，于是被 G1 判成「名单外未追踪文件」。
   **修法不是给它开后门**（加白名单例外会静默掩盖「名单没入库」这个真问题），而是**让它必须入库**：自检仓库里把名单和其它文件一起 commit，于是「名单未入库」会被 G1 自然抓住 —— **这正是我们想要的行为**（闸的配置必须随代码走，否则换机即失效）。
2. **★ G0 失败引发级联误报**：名单不合规时，`allow_norm` 不完整 ⇒ G1 也跟着红 ⇒ 同一个根因报两条红，会把修的人引向「去修 G1」。
   修法：G0 红时 G1/G2/G3/G6 一律标 `not_run` 并写明「因 G0 未通过，名单不可信」。这正是 NC-67 已立过的原则 —— **两种失败必须给不同原因**。

> 这两个都是在「写完判据先拿已知命中样本验召回」这一步抓出来的，不是靠读代码看出来的。
