### 0.2 `turns_used` 的真实语义（读源码确认，不推测）

`gen_candidates_v2.js:185-256`：`for (turn = 1; turn <= maxTurns; turn++)`，每轮一次 LLM 调用；
- 第 1 轮解析/校验失败 ⇒ 把错误清单推回去，进入第 2 轮；
- 校验通过（或 L2 目录下出澄清）⇒ **当轮 break**，`turns_used = 该轮号`。

⇒ **`turns_used` 是「LLM 调用轮数」，不是「修复轮数」**；修复轮数 = `turns_used - 1`。
实测不变量（128 条候选**无一例外**）：`turns_used == len(validation_history) + 1`。

## 1. 口径定义（三层，缺一层这个 KPI 就是自欺）

| 层 | 名字 | 分子 / 分母 | 谁在判 |
|---|---|---|---|
| **L1 结构层** | 修复成功率（schema/contract repair） | 首轮结构未过的题中，在 `--max-turns 3` 内产出**可判记录**（`spec` 非空或 `clarify` 非空）的比例 | `gen_candidates_v2.js` 的 `validate()` + `contractErrors()` |
| **L2 产出层** | 修复去向（spec / clarify / 耗尽） | 修复成功的题分别产出什么 | 同上 |
| **L3 语义层** | 修复后的正确率 | 结构修好了、`spec_fidelity` 全对才算过 | `score_baseline.py` 的 TSR |

**B3 的「修复成功率 ≥ 70%」阈值只管 L1**，这点必须写死：L1 达标不等于模型会建模。

**拒答准确率**明标 `not_computable`：需要「越界题 / 拒答题」题型，而 B5 的 5 类题里**只完成了扩族**，这类题一条都没有。分母不存在 ⇒ 不印数字（R-A3：不许印没量过的数）。

## 3. 为什么必须是「对账闸」而不是「一次性算个数」

单跑一次统计，只能证明「我这次算出来的数是这个」。真正的风险是**两套实现漂移**：候选文件由生成阶段写出，成绩单由评分阶段写出，`turns_histogram` / `first_pass_valid` / `n_unresolved` 是**第二个程序**从同一批候选里数出来的。如果我另写一段统计而不对账，两边一旦不一致，谁都不知道。

所以闸做的是**交叉对账**（两份独立产物，两个程序写出）：

| # | 对账项 | 红意味着什么 |
|---|---|---|
| C1 | 候选文件实读的 `turns_used` 直方图 == 成绩单 `turns_histogram` | 两套统计口径漂了 |
| C2 | `first_pass_valid` == 直方图的 `turns=1` 计数 | 同上 |
| C3 | 成绩单 `n_unresolved` == 候选侧「`spec` 与 `clarify` 均空」条数 | 两套「未收敛」定义不同 |
| C5 | `turns_used == len(validation_history)+1` 全员成立 | 我对 turns 语义的理解错了（**这条红了，整套定义作废**） |
| C6 | 分母（首轮未过的题数）> 0 | 空壳：全首轮通过时 100% 毫无意义，必须判红不判绿 |
| C7 | 逐题 `category` 与候选侧 `(spec, clarify, 期望澄清)` 一致 | 判分器与生成器的产物对不上 |
