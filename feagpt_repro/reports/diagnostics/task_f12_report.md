## 1. 结论先行

`_d3_normalize_eol.py` 原来的扫描源是 `git ls-files`，**只含已追踪文件** ⇒
**每一个新写出来的文件都会漏一次**。危险的不是漏，是**漏得毫无征兆**：

| 检查 | 漏的时候会说什么 | 为什么 |
|---|---|---|
| 工具自己复验 | 「待处理 **0** 个」 | 它扫的集合里根本没有那个文件 |
| `git status --porcelain` | 干净 | `text=auto` 归一后，工作区 CRLF 与索引 LF **归一为同一份**，无差异可报 |

⇒ **两条检查都说没事**，而漂移面（本机 LF / clone CRLF）已经形成。
唯一能看见它的是**跨仓库 clone** 之后的 C7 —— 也就是说，代价要等到别人 clone 时才付。

根因一句话：**闸的输入集合没有覆盖它要守的对象**，而这与 R58「无工具读的 = 无闸」是同一族问题的另一面 ——
那条讲「没有工具就等于没有闸」，这条讲「有工具但看不见对象，等于假闸」。

### 1.1 三次现场（都在 2026-11-01）

| # | 场景 | 结果 |
|---|---|---|
| ① | `_f9_artifact_freshness.py` 新建后未 `add` 就跑 dry-run | 报「待处理 0」，入库后 C7 红 |
| ② | 用 `cat >>` 往已追踪的日志文件追加内容 | 追加部分是 LF，整体变 mixed；dry-run 报「待处理 0」 |
| ③ | 用 `newline=''` 写回 md | 同上，写回段是 LF |

三次都不是「忘了跑工具」，而是**跑了工具、工具说没事**。这才是要修的地方。

## 2. 修法

扫描源：`git ls-files` → `git ls-files --cached --others --exclude-standard`。
`--exclude-standard` 保证被 `.gitignore` 忽略的产物（`_handoff/`、`eval_runs/`、`_probe_*`）不会进来；
实测当前仓库未追踪且非忽略的只有 **1 个**（根目录白名单 md），所以扩集合是安全的。

输出也从「只报个数」改成**逐个点名**：

```
扫描 2344 个（已追踪 2342 + 未追踪 2）；分类 {'lf': 3, 'crlf': 2273, ...}
待处理(dry-run): 1 个（其中属性要求 LF 的 0 个）
   LF->CRLF  _probe_f12_untracked.txt
```

理由：原先只说「待处理 N 个」，想知道是谁还得另开一条命令查 —— 而 F-12 的教训恰恰是
**「两条检查都说没事」，最该有的是第三条、也是最直接的那条**。

### 3.1 自检 5 向 → 6 向（T6 三向）

| 向 | 断言 | 结果 |
|---|---|---|
| T6a | 临时仓库里写一个 LF 文件、**不 add** ⇒ 必须进入扫描集 | ok |

**夹具成员数必须先数清楚，否则判据会假红**。修法是先 `git add .gitattributes`（真实仓库里它本来就已追踪）。

## 4. 边界（诚实说）

1. **不改行尾口径**：仓库仍 CRLF、`*.sh` 仍 LF。本项只扩「看不看得见」。
2. **不改变推荐顺序**：`git add` → `--apply` → 提交 仍是最省事的顺序；只是工具**不再依赖**这个顺序。
3. **守不住「提交后又被别的东西改写」**：本闸管的就是提交前这一关；提交钩子只管暂存区与工作区一致，不管行尾。
4. **未追踪集合目前只有 1 个文件**，所以本项在真实仓库上的「净收益」今天是 0 —— 它的价值在未来（每个新文件）。
